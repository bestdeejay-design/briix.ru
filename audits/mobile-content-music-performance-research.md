# BRIIX Studio: ресёрч мобильного UX и производительности

**Дата:** 2026-11-13. **Назначение:** исследование и план, не заявка о выполненных оптимизациях. Исходный материал кода — рабочий снимок текущей ветки `arena/5784afb1-briix-ru`; файлы студии сверены по Git blob с головой чернового PR #99 `b6d2f48`. Это **не утверждение, что PR уже развёрнут**. Пять проверенных файлов: `studio/index.html`, `studio/studio.css`, `studio/studio.js`, `studio/session-store.js`, `studio/waveform.js`. В процессе исследования продуктовый код не изменялся.

**Что понимаю под максимальным performance:** быстро начать и довести идею до результата, сохранить возможность продолжать работать, быстро слышать трек, не перегревать и не перегружать телефон, не тратить лишний трафик, не терять данные и не создавать ложное ощущение готовности. Сюда входят эстетика и понятность действий, а не только оценка Lighthouse. Время вычисления модели на сервере отделяем от времени интерфейса, очереди и получения медиа: оптимизация кнопки сама по себе не ускоряет инференс.

## 1. Главный вывод

1. **Главный выигрыш — не «ещё больше кнопок», а один быстрый основной сценарий:** идея → понятное подтверждение → работа параллельно → готовая карточка → прослушать/изменить/скачать. Второстепенное — в меню, но важные состояния, ошибки и возврат в сессию не прячутся.
2. В текущей ветке наиболее вероятные технические узкие места — **полные загрузки аудио и восстановление множества файлов**, нагрузка на ограниченный API, полный пересбор библиотечных карточек и копирование всех сессий при каждом сохранении. Это **статические гипотезы, не доказанный профиль iPhone**; порядок исправлений подтвердить замером.
3. Лучший целевой аудиопуть — небольшой ресурс реальных пиков + нативное потоковое воспроизведение с Range, если инфраструктура подтвердит безопасный контракт. Сейчас для большого файла остаётся обычный плеер; нельзя рисовать случайную «осциллограмму».
4. Сначала безопасность данных, корректность сессий и доступность, затем оптимизация по профилю; ни одно ускорение не оправдывает удаление истории, утечку ключа или изменение владельческого запрета на настройку длительности генерации.

## 3. Как должна выглядеть быстрая и эстетичная мобильная студия

**Один экран — одна доминирующая задача.** Вверху компактная идентификация сессии и история. Внизу — composer с одним главным действием; выбор режима и мелкие настройки не должны занимать большую часть экрана с открытой клавиатурой. Результаты — в прокручиваемой ленте. Действие «Новый чат» сохраняет предыдущую работу; состояние сохранения показывается только когда это достоверно.

**Трек в ленте и библиотеке:** миниатюра, название/понятный промпт, одно очевидное play/pause, статус, переход к исходной сессии. Второстепенные «повтор», «обложка», «скачать», «удалить» — логично сгруппированы; частотность первичных действий надо проверить у владельца. Сворачиваемые подробности лирики и настроек. Одна активная дорожка и стабильный плеер при переходах; текущий вариант native controls остаётся безопасным fallback. Показывать только настоящую звуковую форму, текстовое представление позиции и не требовать исключительно drag.

**Изображение:** prompt редактируемый → генерация → предпросмотр → скачать/повторить/отменить; для трека прямо сообщать «отдельное изображение, не заменяет обложку в файле». Нет тихой перезаписи оригинала. **Очередь:** мгновенный отклик на нажатие, реальные состояния «отправляем → в очереди → обрабатываем → готово/ошибка», без выдуманного процента или оставшегося времени. Чат остаётся доступным во время медиа; пользователь должен видеть, где выполняется каждая операция.

**Визуальные правила:** отступы и иерархия по токенам, не засорять интерфейс капсом/мелким серым текстом, раскрывать второстепенное, не передвигать скролл без причины, не создавать длинную колонну отдельных кнопок на 320 px. Текущая карточка библиотеки уже делит действия через «Ещё», но нативный плеер, кнопка waveform и остальные действия всё равно могут занимать значительную высоту; оценка — по ранее снятому headless 320 px, не iPhone. Реальное визуальное решение требует проверки с содержательными обложками, длинными названиями и клавиатурой.

**Доступность как часть скорости работы:** Apple рекомендует touch-target 44×44 pt [1](https://developer.apple.com/design/tips/); WCAG 2.2 AA задаёт минимум 24×24 CSS px с оговорёнными исключениями, а обычный текст — 4.5:1 [2](https://www.w3.org/TR/WCAG22/). Не смешивать Apple points с CSS px как формально одинаковые единицы. Проверять focus/VoiceOver, крупный текст и клавиатуру; мобильная клавиатура может менять visual viewport, не layout viewport [1](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport). Это проверять на реальном Safari, а не только viewport эмуляции.

## 4. Аудит текущего кода: что действительно видно и чего пока не знаем

| Наблюдение в ветке PR | Риск / влияние | Уверенность |
|---|---|---|
| `studio/studio.js:287–322` `feedRestore()` итерирует все сохранённые media и сразу вызывает `fileBlob(d.file)`, даже вне экрана; эти вызовы не проходят через `libQueue`. | При возврате в длинную сессию множество полных файлов могут конкурировать с чатом и обложками. | Факт кода; масштаб и реальная задержка не измерены. |
| `fileBlob()` (`:901+`) читает `response.blob()` целиком; library `libMedia()` (`:1492+`) запускается IntersectionObserver, несмотря на текст «нажмите ▶». | Ленивая по видимости ≠ ленивая по нажатию; полная передача перед воспроизведением, память и данные. В библиотеке очередь ограничена двумя задачами, но feed и polling к ней не относятся. | Факт кода; сеть/память не измерены. |

| `renderLibrary()` (`:1229+`) сначала строит локальный список, затем очищает и строит объединённый заново. `blobCache`, `blobBytes` и `feedObjectUrls` хранят ссылки до удаления/выхода; отдельные пути могут повторно получать один файл. | Повторный DOM, прерывание плеера при обновлении, рост удерживаемых blob URL/данных в долгом сеансе. | `persistSessions()` (`:249+`) синхронно делает `JSON.stringify` + `JSON.parse` **всего** профиля перед каждой очередью; `session-store.js` пишет весь профиль целиком с CAS, включая legacy backup. | Стоимость и объём записи растут с историей. Fallback `localStorage` тоже синхронен [1](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API). | Факт структуры; влияние на iPhone не измерено. |
| `studio/waveform.js`: декодирование только по кнопке, одно одновременно, порог входного blob 8 MiB и 60 секунд воспроизведения; цикл по PCM на JS main thread. Никакого ограничения длительности генерации здесь нет. | Факт кода; нет измерения пика памяти/Safari. |
| `createChat()` обновляет текст при приходе каждого SSE chunk и вызывает `scrollFeed()`; feed — `aria-live`. | Потенциальные лишние layout/paint и частые объявления AT; необходимо профилировать реальные chunks и VoiceOver. | Гипотеза, не доказанный регресс. |
| Размеры исходных статических файлов: HTML **11 881 B**, CSS **27 956 B**, `studio.js` **93 755 B**, `session-store.js` **12 556 B**, `waveform.js` **5 882 B**, `wait-ui.js` **6 914 B**, `wait-phrases.js` **24 605 B**. | Сумма **183 549 B raw / 50 734 B gzip** (`gzip -n` каждого файла локально). Это не сетевой transfer size: сжатие, cache headers, HTTP-накладные расходы и фактические обращения на стенде неизвестны. Не оптимизировать байты вслепую раньше медиа и API. | Локальное измерение файлов; не LCP и не реальные измерения трафика. |

**Небольшой воспроизводимый CPU-эксперимент, не мобильный benchmark:** на sandbox Node.js, 30 замеров после 5 прогревов, `JSON.parse(JSON.stringify(profile))` для синтетических текстовых событий: 100 / 1 000 / 5 000 событий, **36 456 / 364 056 / 1 824 056 B** JSON, медиана **0,082 / 1,167 / 6,964 мс**, p95 **0,635 / 2,082 / 9,259 мс**. Это только операция копирования на серверном CPU в Node, без IndexedDB, UI и треков; **нельзя переносить эти числа на Safari/iPhone или считать обещанием результата**. Цель эксперимента — показать необходимость профилирования роста и write amplification, а не доказать лаг.

Не добавлять CDN и обязательную сборку. | Оптимизация должна улучшить трассу, а не создавать лишний network waterfall; команды UI работают сразу. |
| **P2 — системное управление медиа** | Если поддерживается браузером, Media Session для метаданных и управления через lock screen/headset, сохраняя native controls. [2](https://developer.mozilla.org/en-US/docs/Web/API/Media_Session_API) | Удобство на телефоне, но поддержка/фоновые ограничения различаются; не считать гарантированным на всех iOS. | Проверить lock screen, прерывание звонком, Bluetooth, возврат из background и без автозапуска. |

## 6. Аудиоконтракт: клиент против INFRA

1. **Сегодня:** `fetch` с bearer → полный `Blob` → object URL → `<audio>`. Это защищает токен при текущем контракте, но может задержать первый звук и потреблять много трафика. Не добавлять токен в query string, логи или скачиваемые URL.
2. **Целевое постепенное воспроизведение:** `<audio src>` не предоставляет интерфейса для произвольного `Authorization` header; поэтому простой перевод на URL `/files/...` **не совместим автоматически** с текущей bearer-защитой. INFRA должна предложить безопасный same-origin cookie/proxy либо ограниченный по времени и области media URL после оценки утечки/редакции логов, рефереров, кеша, отзыва и межпрофильной изоляции. Не изобретать незадокументированный API.
3. Верифицировать `Range: bytes=...`, `206`, `Content-Range`, `416`, MIME и перемотку; отсутствие корректной Range-поддержки не следует считать существующей проблемой сервера без замера. [1](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)
4. Peaks/thumbnail генерировать вне критического пути старта audio либо измерять влияние на очередь генерации; версионировать относительно конкретного аудио/обложки, не отдавать чужие данные. Cache-Control для персонального контента должен быть согласован (например, `private` или более строгий режим по требованиям), не использовать shared public cache для приватных файлов [1](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control).
5. Retention, audio-to-audio и прикрепление версии обложки — INFRA #94/#95, статус живого стенда не проверен. Локальная история не гарантирует сохранение аудио на сервере.

## 7. План замеров и продуктовые KPI

**Не обещание и не текущие результаты.** Для web-витальных ориентиров: LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1 на p75 реальных визитов [1](https://web.dev/articles/defining-core-web-vitals-thresholds). Lighthouse не измеряет реальный INP без пользовательских действий; TBT — лишь лабораторный proxy [2](https://web.dev/articles/vitals). Safari может не поддерживать те же PerformanceObserver entry types; проверять `supportedEntryTypes`, не делать вид, что отсутствие метрики = хороший результат [1](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceObserver/supportedEntryTypes_static).

| Пользовательский показатель | Начало → конец / оговорка | Предлагаемый ориентир, не SLA |
|---|---|---|
| Готовность экрана | navigationStart → composer видим и доступен для ввода | Ориентир LCP + отдельная проверка фактической интерактивности. |
| Отклик на Create | tap → первая честная визуальная обратная связь, не готовность модели | Цель p75 ≤100–150 мс в согласованном профиле; сервер не включать. |
| ACK job | tap → подтверждённый `job_id` | Измерять p50/p75/p95, отдельно сеть и 429; цель назначить после baseline. |
| Очередь / инференс / упаковка | `job_id` → очередь → готовность (если сервер отдаёт достоверные timestamps) | Метрики раздельно; не выдавать ожидание за ускорение модели. |
| Первый звук | tap Play → событие `playing` и, при возможности, реальная аудиопроверка | Замер отдельно cold/warm, на авторизованном реальном сервере; факт `playing` сам по себе не гарантирует слышимость. |
| Эффективность работы | время от открытия до первого сохранённого/прослушанного результата; доля завершённых созданий среди начатых, доля успешных возвращений в сессию | Нужны определение события, consent, размер выборки и контрольные группы; не интерпретировать кратковременные цифры как доказанную конверсию. |
| Ресурсы | сетевые байты и запросы по категориям, 429, frame/long tasks где доступны, память/тепло/батарея по физическому устройству | Сначала baseline. Для 100 треков без play — предложенный бюджет 0 полных audio GET и сохранение всех данных. |

**Матрица:** iPhone Safari (модель владельца + более старый поддерживаемый iPhone), Android Chrome на устройстве среднего/начального класса; 320/360/390 CSS px, portrait/landscape, 200% text zoom, экранная клавиатура, VoiceOver/TalkBack, слабая и нестабильная сеть, warm/cold cache, фон, low power, быстрые повторные переключения. Модель и iOS фиксировать в отчёте, не объявлять headless Chromium тестом Safari. Safari Web Inspector может записывать Network, Timelines, память и CPU [1](https://developer.apple.com/safari/tools/).

**Метод:** до/после на одном commit/fixture и тех же настройках; минимум 30 повторов на сценарий как начальная лабораторная оценка, показывать распределение и диапазон, не называть 30 выборок достоверным p95 реальных пользователей. Повторить в разные моменты и на реальных сетях. В production — отдельное разрешение на RUM, ограниченное время и агрегация; не отправлять приватные данные, не добавлять внешние аналитические скрипты без согласования. `navigator.connection` и Save-Data не везде доступны, поэтому режим экономии трафика должен иметь явный пользовательский выбор и безопасный дефолт [1](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/connection).
