## 1. Что просим поставить агенту

Просим предоставить **единую приватную шину к уже доступным и разрешённым моделям BRIIX**, а не отдельные несвязанные API для каждой вкладки демо.

Минимальный результат для текущего демо:

1. **Чат:** живой текстовый ответ существующей `qwen3:4b-instruct` через согласованный chat-маршрут; стриминг, остановка и ошибка mid-stream.
2. **Фото:** асинхронная генерация FLUX.2-klein-4B через очередь, получение PNG и provenance.
3. **Музыка:** асинхронная генерация MusicGen small через ту же очередь, получение WAV и provenance. В UI это инструментальная музыка, не песня с вокалом.
4. **Каталог:** браузер получает только публичные ID и capabilities реально включённых маршрутов; выключенная модель не выглядит доступной.
5. **Расширение:** новые модели подключаются адаптером за шиной без переписывания UI. Речь, ASR, видео и вокальные песни добавляются только после отдельной проверки ресурсов/лицензии и появления capability.

«Ко всем моделям» означает все **разрешённые и фактически готовые** маршруты текущего контура. Это не обещание одновременно запустить все исследовательские модели из справки и не скрытый fallback на другую модель.

### Что вернуть в BRIIX для подключения UI

- адрес приватного origin/base path и способ подъёма туннеля **без публикации секретов в Git**;
- OpenAPI 3.1 или эквивалентный версионированный contract pack для JSON endpoints, плюс описание SSE;
- фактический каталог моделей: public ID, capability, статус, лимиты, лицензия/назначение, measured/estimated latency;
- примеры успешных запросов и ошибок для chat/image/music;
- правила auth, CORS/CSRF, idempotency, cancel, retry, TTL файлов и восстановления после reload;
- безопасные smoke-артефакты: текстовый ответ, PNG, WAV, job trace и замеры без внутренних адресов/ключей;
- команда/инструкция «поднять контур» и «погасить контур», проверенная исполнителем #23;
- контакт/точка передачи контракта frontend-исполнителю. До передачи контракта не просим frontend угадывать поля.

## 3. Предлагаемая форма шины

Одна шина = один origin, одна auth-схема, один каталог, единые ошибки/request ID и provenance. Транспорт может быть разным: синхронный/SSE для чата и асинхронные jobs для тяжёлых медиа. Это нормальнее, чем держать HTTP-соединение открытым десятки минут ради песни.

| Endpoint | Статус имени | Назначение |
|---|---|---|
| `GET /v1/models` | проект API.md | доступные модели и capabilities текущего ключа/сессии |
| `POST /v1/chat/completions` | проект API.md / П-5 | живой чат, JSON или SSE по `stream` |
| `POST /jobs` | закреплён в #23 | принять image/music job, вернуть `202` и `job_id` |
| `GET /jobs/{job_id}` | предложить, закрепить в OpenAPI | статус, фактическая модель, ошибки, ссылки на результат |
| `POST /jobs/{job_id}/cancel` | предложить, закрепить в OpenAPI | отмена queued/running с честным итогом |
| `GET /files/{id}` | закреплён в комментарии #23 | скачивание результата с авторизацией, без base64 в localStorage |

Имена job-status/cancel и точные payload пока не считаем реализованными. Финальный источник истины — контракт исполнителя #23.

### 3.1. Каталог и capabilities

Минимальные поля сверх базового OpenAI-подобного объекта:

```json
{
  "id": "<public-model-id>",
  "object": "model",
  "capabilities": ["music.generate"],
  "status": "ready",
  "limits": {
    "max_duration_seconds": 30,
    "max_concurrent_jobs": 1
  },
  "license_scope": "demo-only",
  "latency": {
    "source": "measured",
    "seconds": 60,
    "conditions": "15 s audio, CPU quota 8 threads"
  }
}
```

Это иллюстрация формы, не готовый ответ сервера. Capability явно разделяют `chat`, `image.generate`, `music.generate`, `song.vocal`, `audio.tts`, `audio.transcribe`, `video.generate`. Не обещать capability, если маршрут не прошёл smoke test.

### 3.2. Чат

- сохранить контракт `model`, `messages`, `stream`, лимиты вывода из API.md;
- фактическая модель возвращается в ответе; подмена помощника/модели без явного правила запрещена;
- SSE: порядок chunk, финальный маркер, heartbeat/timeout, disconnect/cancel, ошибка после начала потока;
- история передаётся клиентом в пределах лимита; server retention по умолчанию не включать без отдельного решения;
- usage помечать `exact` / `estimated` / `unavailable`, не выдавать оценку за точный учёт.

### 3.3. Медиа-очередь

- `POST /jobs` возвращает `202` только после durable принятия задачи; клиент не рисует фиктивный прогресс;
- серверные состояния минимум `queued`, `running`, `ready`, `error`, `cancelled`; `interrupted` из #23 — состояние клиента при потере связи, не выдуманный серверный результат;
- если процент не известен, UI показывает indeterminate progress и стадию, а не таймер «почти готово»;
- результат содержит `file_id`, MIME, размер, checksum, фактическую модель/версию, параметры, timestamps и длительность;
- повтор создания защищён `Idempotency-Key`/документированным client request ID; retry после начала генерации не создаёт дубль молча;
- cancel queued не запускает задачу; cancel running завершает работу или честно сообщает, что backend не поддерживает немедленную отмену;
- TTL/очистка файлов возвращает понятное «результат истёк», а не битую картинку;
- после reload клиент восстанавливает job по серверному ID, а не перезапускает генерацию.

## 4. Приватный доступ и безопасность

Целевой сценарий — текущее демо на приватном стенде/туннеле, не публичный запуск на GitHub Pages.

1. Предпочтительно один same-origin контур: статические файлы демо и API за одним локальным reverse proxy. Браузер использует относительные `/v1/...`, `/jobs`, `/files/...`.
2. Браузер пользователя не обращается к `localhost`/LAN-адресу сервера и не знает upstream endpoints. SSH-туннель поднимает координатор/пользователь по инструкции, не frontend-код.
3. Публичный Pages-режим остаётся offline/local-mock и не делает внешних запросов. Live включается только явной приватной конфигурацией и видимой маркировкой.
4. Upstream/master/API-ключи не попадают в HTML, JS, localStorage, URL, логи или Git. Для `GET /files/{id}` с bearer из #23 уточнить класс токена: это должна быть ограниченная demo/session credential, а не ключ fonotext/Ollama/provider. Не сохранять долговременный ключ в localStorage.
5. Если выбран cookie-session: `HttpOnly`, `Secure`, подходящий `SameSite`, CSRF-защита для изменяющих запросов. Если выбран memory bearer: короткий TTL, scope, revoke и явное описание хранения.
6. CORS allowlist только утверждённых приватных origins; wildcard с credentials запрещён. Ошибки не раскрывают hostname, stack, prompt или secret.
7. До отправки первого live-запроса UI сообщает, что текст/промпт покидает браузер и уходит в приватный контур. Retention и удаление результатов согласовать с #23/R2.
8. Публичный ingress/Caddy/DNS не менять в рамках этого запроса. Публикация наружу — отдельное решение владельца и П-13/R2.

## 5. Ресурсы и маршруты

Опираемся на `docs/fonotext-stands-brief.md` и ограничения #23, а не на сумму RAM двух серверов:

- A: 20 ядер / 94 ГБ RAM; приоритет fonotext, CI и существующей панели; генерации BRIIX ≤8 тредов суммарно, RAM-бюджет нашего контура ~10 ГБ max по #23;
- B: RTX 3050 8 ГБ / 12 ядер / 31 ГиБ RAM, egress закрыт; Silero/Whisper/Ollama уже заняты. Подключение B к шине — только через координатора, файлами и после отдельного ресурсного решения;
- NFS заполнен на 99%: веса/результаты туда не писать;
- агенты BRIIX не ходят на стенды напрямую; доступ выдаёт координатор под задачу;
- тяжёлые media jobs планировать последовательно в рамках квоты. Не запускать FLUX и вокальную модель параллельно только потому, что в сервере 94 ГБ RAM;
- текстовый маршрут не должен выгружать/перезагружать fonotext-инстансы. Комментарий #23 уже зафиксировал отсутствие отдельного текстового порта: создание/выбор маршрута делает INFRA после RAM-гейта.

## 6. Музыка с вокалом: отдельный маршрут, не подмена MusicGen

MusicGen small уже измерен и подходит для инструментальных лупов. Он не закрывает просьбу владельца о полноценных песнях с хорошим вокалом.

Просим добавить в план INFRA **отдельный опциональный vocal-route**:

1. Первый кандидат — ACE-Step 1.5 через C++/GGML `acestep.cpp` и GGUF. Официальный проект заявляет CPU inference и MIT; модельная карточка указывает MIT и коммерческое использование outputs. Русский входит в поддерживаемые языки. Источники: [1](https://github.com/ace-step/ACE-Step-1.5), [2](https://huggingface.co/ACE-Step/Ace-Step1.5), [1](https://github.com/ServeurpersoCom/acestep.cpp), [1](https://huggingface.co/docs/diffusers/api/pipelines/ace_step).
2. Проверить конкретные веса/кванты, license notice, AVX2-сборку, пиковую RAM и реальное время на A. Не переносить GPU-бенчмарки в отчёт как CPU-замеры.
3. Начать с 30–60 секунд русской лирики, структурных тегов и нескольких кандидатов; сравнить turbo/sft по вокалу. Хороший вокал не гарантировать до прослушивания.
4. Не превышать RAM/CPU-бюджет #23. Если маршрут не помещается, вернуть `unavailable`/план отдельного окна, а не молча тормозить весь контур.
5. HeartMuLa 3B — второй кандидат для сравнения вокала (Apache-2.0, но CPU может занимать десятки минут); DiffRhythm 2 — резерв Apache-2.0. YuE2/LeVo 2 не включать в коммерческий маршрут без проверки лицензий весов и ресурсов.
6. MusicGen и ACE-Step должны иметь разные public model IDs/capabilities. UI не должен подписывать инструментал как «песня с вокалом».

Vocal-route не блокирует приёмку первых трёх маршрутов #23, если координатор явно разделит этапы. Но он должен остаться в плане, иначе просьба владельца о песнях будет формально закрыта неподходящей моделью.

## 7. Как это ляжет на текущее демо после передачи контракта

Этот раздел — предложение для следующего frontend-этапа, не выполненная правка.

| Место в текущем демо | Что меняется после контракта |
|---|---|
| `demo.js`, отправка сообщения | сценарный generator заменяется live-адаптером только в явно включённом режиме; stop становится Abort/cancel; сохраняются история и избранное |
| Подписи чата | `Демо-ответ` / `Локальный диалог` не остаются на реальном ответе; показываются live-модель и приватная отправка данных |
| `media.js` + новый `media-live.js` по #23 | локальный timer остаётся в local-mock; live job создаётся через `POST /jobs`, статус приходит polling, результат через `/files/{id}` |
| Медиатека | metadata/provenance отдельно от blobs; миграция `media-v1` → `media-v2` без потери существующих записей, как закреплено в #23 |
| Очередь | реальные queued/running/ready/error/cancel, отмена и восстановление после reload; client `interrupted` при потере связи |
| Модели | справочный каталог не выдаётся за список установленных; live-каталог приходит из `/v1/models` |
| Ошибки | при падении шины demo не ломается; нет тихого переключения уже отправленного live-запроса на мок |

Режимы интерфейса: `local-mock`, `curated`, `live`, `unavailable`. Переход в mock после ошибки — только явное действие пользователя с маркировкой. Публичная статика по умолчанию не получает сетевой конфигурации.

- [ ] Музыка: реальный WAV из MusicGen, явно instrumental/demo-only.
- [ ] Vocal-route: план/замер ACE-Step либо явный `unavailable` с причиной; не подменён MusicGen.
- [ ] Auth/CORS/CSRF и отсутствие секретов в браузере/Git проверены.
- [ ] Единый error envelope/request ID, idempotency и безопасный retry описаны.
- [ ] Замеры задержек и влияния на fonotext записаны; квота ≤8 тредов и RAM-гейт соблюдены.
- [ ] Контур поднимается/гасится документированной командой; публичный ingress не изменён.
- [ ] Frontend-исполнитель получил контракт и безопасные fixtures; независимое ревью не-автором назначено координатором.
