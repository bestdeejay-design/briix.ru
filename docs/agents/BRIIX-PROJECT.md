саморевью исключено и при делегировании (канон PROTOCOL §1): пока второго агента
на гейт/ревью нет, поставка помечается «ревью не-автором не назначено».

## 2. Уровни окружений (канон: test → staging → production)

| Уровень канона | Механика briix |
|---|---|
| test | ветка исполнителя + полный локальный регресс (§4) |
| staging | PR на GitHub + ревью не-автором (approve на точный head-коммит); проверка локальных ссылок изменённых страниц |
| production | `main` → GitHub Pages https://briix.ru/ (авто-билд, CNAME `briix.ru`) |

- Self-merge исполнителя в `main` запрещён (Правило 2 briix): слияние в main =
  промоушен в production, делает координатор после approve ревьювера. Исключение —
  прямое поручение владельца (как 07.11 для этой сессии), фиксируется в отчёте.
- Пост-деплой верификация (канон PROTOCOL §6): после промоушена сверять живой ответ
  `https://briix.ru/` (HTTP 200) и целевые файлы; пуш в main без изменения файлов
  сайта считается чисто процессным деплоем.
- Файлы процессного слоя (`docs/agents/`, `audits/`) публикуются Pages как статика
  — это осознанное следствие публичного репозитория, отдельная изоляция не настроена.

## 3. Размеры (S/M/L) на примерах briix

- **size:S** — правка 1–3 файлов без смены интерфейсов: точечный фикс вёрстки/текста,
  правка одного блока `demo.css`, обновление отчёта в `audits/`. Fast-Track дуэт,
  без паузы GATE OPEN до кода.
- **size:M** — один модуль: правки в `assets/js/*` или одной странице + её стили,
  новая секция лендинга в RU и EN. Полный ARCA: AUDIT → RESEARCH → CONCLUSION-гейт → ACTION.
- **size:L** — несколько модулей/интерфейсы: новая страница с зеркалом `en/` и общими
  стилями, перенос структуры сайта (как перенос `site/` в корень), смена дизайн-системы.
  Как M + ADR `proposed` → `accepted` координатором.

## 4. Канонический регресс briix (полный список; сокращать нельзя)

```bash
git fetch origin && git merge-base --is-ancestor origin/main HEAD   # база свежая
node --check assets/js/landing.js && node --check assets/js/theme.js
node --check demo.js demo-data.js media.js                          # когда в радиусе
grep -c '\[hidden\]' assets/css/main.css                            # ≥ 1, хотфикс модалок
grep -c '^\[data-theme' assets/css/main.css                         # ≥ 1, тёмная тема
python3 -c "s=open('assets/css/main.css').read(); print(s.count('{'), s.count('}'))"  # скобки сходятся
grep -nE '^(<{7}|={7}|>{7})' assets/css/main.css assets/js/*.js     # пусто: маркеры конфликтов
grep -c '\.btn {' assets/css/main.css                               # ≥ 1, базовые кнопки живы
grep -c '@media print {' assets/css/main.css                        # ≥ 1, печать PDF жива
ls en/index.html en/presentation.html                               # английское зеркало на месте
# + проверка локальных ссылок по изменённым HTML-страницам (битых быть не должно)
```

Красный регресс — сначала атрибуция на базовом коммите (канон PROTOCOL §6), потом разбор диффа.

## 5. Святые зоны (замороженные; правка — только явным словом владельца)

- Цветовые токены в `assets/css/main.css`: цвета только в `:root` / `[data-theme]` / `@media print`.
- Правило `[hidden] { display: none !important; }` в начале CSS.
- Константа `--container: 1160px`.
- `docs/` — канон продукта (`BRIIX.md` и др.): только читать. Процессный подкаталог
  `docs/agents/` — исключение, разрешено владельцем 07.11.2026.
- Статик без сборки: без npm, бандлеров, фреймворков, внешних CDN; шрифты self-hosted
  с кириллическими подмножествами.

## 6. Поставка и сигналы

- **Письмо о поставке** (`📬 DELIVERED`): в briix — файл `audits/task-<N>-<имя>.md` в ветке
  поставки (Правило 3 briix); обязательные поля канона §4.4 AGENT_RULES + «что осталось
  непроверенным». Поставка без письма не существует.
- **Маркеры шины** — дословно по KNOWLEDGE_BASE §5, вторая строка — подпись
  `— <роль> · сессия <ид>`. В briix issue используются: `🎯 CONCLUSION`, `📬 DELIVERED`,
  `⛔ BLOCKED`, `❓ QUESTION`, `💓 HEARTBEAT`, `🔎 VERDICT` (sha7) и координаторские
  `✅ GATE OPEN`, `🔁 REJECTED`, `🏁 DONE`, `👤 NEEDS-HUMAN`, `📌 DECISION`.
- **Labels** — словарь варианта C (KNOWLEDGE_BASE §1): на открытой задаче ровно один
  `status:*` и (для M/L) ровно один `phase:*`, ровно один `to:*`; движение статусов —
  только координатор.
- **Зависимости** — нативные GitHub `blocked by`; строка `Depends on: #N` — fallback.
